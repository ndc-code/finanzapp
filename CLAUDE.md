# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository overview

This repo has no build system, package manager, or test suite — it's two static files, deployed as-is via GitHub Pages:

- `index.html` — a single-file web app ("Gastos en pareja" / "Shared couple expenses"), self-contained HTML/CSS/JS with one external JS dependency (`@supabase/supabase-js`, loaded via CDN `<script>` — see Persistence below; fonts are loaded from Google Fonts via `<link>`). This is the actual application.
- `DESIGN.md` — a standalone design-system reference document analyzing Apple's website (colors, typography, spacing, components). It documents a *different* aesthetic (photography-first, blue accent, SF Pro) than what `index.html` currently uses (warm editorial palette: Fraunces serif headings, Inter body, IBM Plex Mono for numbers, gold/clay/paper tones). Treat it as reference/inspiration material, not a spec already applied to the app — don't assume the two are in sync unless asked to reconcile them.

## Running / testing changes

There is no dev server, bundler, or test command. To verify changes, open `index.html` directly in a browser (or use the `run` skill to launch it) and exercise the UI manually — add an expense, toggle paid/unpaid, add income entries, change the split type, etc. Since persistence now goes over the network to Supabase, testing multi-device sync means opening the file in two tabs/browsers and entering the same couple code in both.

## Architecture of index.html

Everything lives in one file: `<style>` in the `<head>`, markup in `<body>`, and app logic in a single trailing `<script>`. There is no framework — DOM updates are done by re-rendering `innerHTML` strings from plain JS state.

**Persistence**: backed by Supabase (Postgres + REST + Realtime), not `localStorage` or `window.storage` (this app previously ran inside Claude Artifacts, where `window.storage` was Artifacts' own shared KV runtime — that environment no longer applies here). Every couple is one row in a `couples` table, keyed by a shared "código de pareja" the two people agree on (no email/password — see `initCouple()`/`enterCouple()`). The `store.get(key)`/`store.set(key, value)` object (search `const store = {` in the script) still exposes the original key-based interface so the ~15 call sites elsewhere didn't need to change; internally it now maps logical keys to `couples` columns and does Supabase `select`/`update` calls:
- `expenses_v1` → `expenses` column — array of expense objects
- `names_v1` → `names` column — ordered `[{id, name}]` roster of the people in the space; the old `{A, B}` object shape is migrated on read by `migratePeople()`
- `income_v2` → `income` column — `{fx, entries: {A: [...], B: [...]}}`; a legacy scalar shape is migrated on load via `migrateIncome()`
- `fixed_v1` → `fixed` column, `fixedincome_v1` → `fixed_income` column
- `varestimates_v1` → `variable_estimates`, `varexpenses_v1` → `variable_expenses`
- `budgetoverrides_v1` → `budget_overrides` — the **gastos posibles** rubros, now `{monthKey: {personId: [{id, label, amount, fx?}]}}` — one independent set of rubros per month (`YYYY-MM`), so editing "Compra dólares" in October never touches September. `budgetTemplatesForMonth(key)` is the only accessor: it lazily creates (and caches into `budgetTemplates`) a month's rubros the first time they're asked for, cloning them from the nearest earlier month that already has some (or `defaultBudgetCats()` if there's none yet) — so a new month starts out looking like the last one instead of empty, but is a full clone from that point on, not a shared reference. The amount is edited in Ajustes or from the ✎ on the rubro's card in Gastos — both call `budgetTemplatesForMonth(viewMonth)`, so they always agree on which month's numbers they're touching. "Compra dólares" additionally carries `fx`, stamped with `usdRate()` whenever its amount is set — every USD display for that rubro (the ⇄ toggle in Gastos, the Ahorro tab's "En dólares" cell) reads `c.fx` instead of the live rate, so it doesn't drift day to day. `migrateBudgetTemplates()` converts the legacy flat shape (`{personId: [...]}`, one set of rubros shared by every month — the bug this per-month split fixes) by copying it into every month that already has real activity, so nothing changes for existing months on upgrade; anything from there on is independent per month.
- `goals_v1` → `goals` column — array of user-written savings goals `{id, person, name, kind:'total'|'mensual', amount, currency, deadline, saved}`
- `debts_v1` → `debts` column — array of personal debts `{id, person, name, kind:'total'|'plan', months, amount, currency, saved}`, one per person (no "Compartido" — see the **Deudas** tab). "Saldada" isn't a stored flag, it's derived (`debtIsDone()`: `saved >= amount` once converted to the same currency). `kind:'plan'` just carries `months` for a reference monthly cuota (`amount/months`, shown, never auto-applied) — "ya juntaste" is always typed in by hand, there's no auto-incrementing like Compra dólares' auto-generated rows.
- `debttemplates_v1` → `debt_templates` column — `{personId: [{id, label, amount}]}`, same flat (no-month) shape as `varEstimates`. Recurring debt names/amounts managed in Ajustes' **Deudas** card; they don't feed `debts` directly — they only populate the quick-pick chips (`dDescChips`) in the "Agregar deuda" modal, same mechanism as `fixed`→`descChips` and `varEstimates`→`vxDescChips`.
- `dailyexpenses_v1` → `daily_expenses` column — gastos diarios (gastos hormiga), same shape as `varExpenses` (`{id, desc, amount, date, paidBy, shares, splitType}`) plus optional `card` (and a legacy `interest`, no longer entered): personal or shared with a payer and split, and they feed `netBalances()` like variables. The modal's "¿Cómo lo pagaste?" is **Transferencia** or **Tarjeta de crédito**. Transferencia (no `card`) is paid out of that person's Salidas + Gustos pool (`dailyTotalOf()`, `wantsBudgetOf()` = every gastos-posibles rubro except Compra dólares) — see the money chain below. Tarjeta stores the card in `card` (`isCardDaily()`): it does **not** touch this month's saldo, it's a debt of the payer (`cardDailyPayer()` = `paidBy`, the whole amount — a shared one's other slice is already owed through "Entre ustedes"), listed in Deudas › **Tarjeta de crédito de [mes]** (`cardSpendIn()`, together with 1-payment `card_purchases`) and paid next month as the auto "Cuotas <tarjeta>" variable expense via `desiredCardExpenses()`/`syncCardExpenses()`. "Borrar mes" never deletes card-paid dailies. Loaded with the null-safe pattern (column may not exist yet).
- **Créditos** are loans — money received that is repaid with interest next month. They have no column of their own: Deudas › "+ Sacar crédito" opens the daily modal's credit form ("ingreso" kind, person locked: ¿De dónde?, Monto, Intereses, Fecha), stored in `card_purchases` with `credit: {received, date}`, `amount = received + intereses`, `months: 1` and `startMonth` = the month after `credit.date`, so `syncCardExpenses()` generates the "Cuotas <origen>" variable expense. `creditReceivedOf()` adds `received` to that person's Salidas + Gustos pool in the month it was taken — deliberately **not** income, so it never shifts the "según ingresos" split. Editing one reopens that form (`openCpModal` redirects when `p.credit`).
- **Créditos de [mes]** (Deudas) is `creditsTakenIn(person, month)` — loans only: one card per origin with the total, expandable when there's more than one into sub-cards named like the card with "fecha · Intereses $X"; the footer (Totales) expands into Monto vs Intereses. Every Gastos block reads as a cascade (saldo anterior − lo del bloque = Saldos): Gastos posibles only holds the Compra dólares card and closes with Saldos = `afterVar − dolares`; Salidas y gustos is not a list of rubros any more but a derived figure — `financeFor().wants = max(0, afterVar − dolares)`, shown as a 60/40 split line (`salidasGustosSplit()`) in Ahorro › Cómo venís este mes. The stored Salidas/Gustos rubros in `budgetTemplates` are ignored by the chain. Under Gastos posibles' "Saldo" (one cell for the open tab's person = `afterVar − dolares`) come two more cells in `#budgetCreditTotal`: a dashed **Crédito** cell (`.sld-dashed`, loans taken that month, capital) and a **Total** cell = `bolsaOf()` — what's available for Gastos diarios. Blocks that show a single person label that step "Saldo" instead of "Saldos". Gastos diarios is the button, person sub-tabs, the list, and a closing Saldos card (`renderDailySaldoFinal()` = `bolsaOf() − dailyTotalOf()`; card-paid dailies and the other person's slice of shared ones don't subtract). The per-loan detail lives in Deudas › Créditos.
- Deudas are always one person's: the person pickers in the Deudas modals (`dWhoSeg`, `cpWhoSeg`, and the daily modal when opened from Deudas) are shown but locked (`.seg-locked`) to the Deudas sub-tab's person.
- Deudas rows use the same `.bill` layout as Gastos (`deudaBillHtml()` / `deudaChildHtml()`): anything with detail (cuotas, monto/intereses) expands like a repeating fixed expense (Limpieza), not as `.goal` progress cards.
- the one-time migration flags (`fixed_m1`, `fixed_m2`, `fixed_m3`, `fixedincome_m1`) collapse into a single `migration_flags` jsonb column instead of separate rows

Adding a new logical key means adding the column to `couples` in Supabase too (`alter table couples add column <name> jsonb;`) — there's no migration runner. A write to a column that doesn't exist comes back through supabase-js as PostgREST error `PGRST204` ("column not found in schema cache"), not the raw Postgres `42703` — `store._writeNow()` special-cases both codes (no retries, and a toast naming the missing column) and the value survives in the localStorage cache until the column exists. **The read side needs the same care**: `store.get()` can't tell "column missing" apart from "column is null", so it returns `null` either way — `loadAll()`'s fetch for a still-columnless key must treat that `null` as "no change" (skip the assignment) rather than resetting the in-memory array to `[]`, or it silently wipes out whatever `paintFromLocalCache()` already loaded from the local cache on every page load until the column is added (see `debts_v1`'s loader for the pattern; `goals_v1`'s older loader predates this fix and doesn't need it in practice only because its column already exists everywhere).

A Supabase Realtime subscription (`subscribeCoupleRealtime()`) pushes every `UPDATE` on the couple's row to all other open tabs/devices with the same code, which is what makes cross-device sync work without polling. Row Level Security on `couples` allows any `anon` client to read/write — the couple code itself is the only access control, mirroring the no-auth model the app already had. The Supabase project URL and anon key are hardcoded near the top of the script (`SUPABASE_URL`, `SUPABASE_ANON_KEY`) — this is intentional and safe: Supabase anon keys are meant to be public, security comes from RLS policies, not from hiding the key.

**Never trust a Realtime payload as a whole row.** `payload.new` can arrive empty (`{}` with an `errors` entry) when the row exceeds Realtime's max payload size — likely for a space with months of history — or missing columns when pushes reorder. `isWholeCoupleRow()` gates this: an incomplete push triggers a `fetchCoupleRow()` refetch instead of being adopted. `applyCoupleRow()` then overwrites each in-memory field **only when the row actually carries it** (`if(Array.isArray(coupleRow.expenses)) expenses = …`) — a missing column means "unchanged", never "empty". The earlier code reset `expenses`/`income` to `[]` on any incomplete payload, which silently wiped whole months of data.

**`bailOnMassWipe()` guards every `save*()`.** A write that takes a non-empty set straight to empty is refused and resynced from the authoritative row — the UI only ever deletes one entry at a time, so a jump to zero is corruption, not intent. `countItems()` handles both array columns and the `{A:[],B:[],shared:[]}` object columns; `prevCol()` reads the last-known count off `coupleRow`. The flows that legitimately clear in bulk — lowering the people count (`setPeopleCount`), `applySnapshot()` — set `allowBulkClear = true` around their saves so the guard doesn't fight them. The check is the first statement in `bailOnMassWipe` (before any `await`) so the fire-and-forget `save*()` calls in `setPeopleCount` clear it synchronously.

**Backups** live in a separate `couple_backups` table (`code`, `created_at`, `label`, `snapshot jsonb`), *not* a column on `couples` — a snapshot column would bloat the row and worsen the Realtime-truncation hazard above. Schema + RLS in `docs/couple_backups.sql` (run once in Supabase; `42P01` from the app means it hasn't been run). The backup module (search `BACKUP_TABLE`) does on-demand `select`/`insert`/`delete` — no Realtime. `currentSnapshot()` captures every data column; `applySnapshot()` restores them in one atomic `update` to `couples`, and every restore path auto-creates an "Antes de restaurar" backup first. `maybeAutoBackup()` (called at the end of `loadAll()`) writes one silent `Copia automática` per space per day — deduped across devices via a `gte(created_at, today)` check and a `last_auto_backup_<code>` localStorage stamp — and `pruneAutoBackups()` keeps the newest `AUTO_BACKUP_KEEP` (14); manual / `Cierre de mes` / `Antes de restaurar` backups are never pruned. Ajustes also exposes `.json` download/upload as a Supabase-independent fallback.

**People model**: a space holds **1 to `MAX_PEOPLE` (4) people**, not a fixed couple. `people` is an ordered array of `{id, name}` where `id` comes from `PERSON_IDS = ['A','B','C','D']`; that id is what every record is keyed by — expense `paidBy` and `shares`, `income.entries`, `varEstimates`, `budgetOverrides`, `goals.person`, `debts.person`, `debtTemplates`, `fixedIncome.person`. Names are cosmetic and resolved at render time through the derived `names` map (`nameOf(id)`), so renaming someone never touches data.

- `pids()` / `peopleCount()` / `firstPid()` / `isPerson(id)` are the accessors; **never hardcode `'A'`/`'B'`** or iterate a literal `['A','B']`.
- `setPeople()` is the only way to change the roster: it rebuilds `names`, creates the missing per-person slots, and re-points any selection (`currentPaidBy`, `currentAhorroPerson`, …) that pointed at someone who is gone.
- **Expense splits** are `ex.shares = {A: 60, B: 40}` (percentages), not the old scalar `pctA`. Build them with `sharesFor(splitType)`; `splitType` is `'equal' | 'income' | 'only:<id>'`. `normalizeExpenses()` migrates `pctA` and the old `'50' | 'a-to-b' | 'b-to-a'` types on load, so stored data from the couple-only era keeps working.
- Raising the count leaves past expenses alone on purpose — those months really were split among whoever was there, and the newcomer's share is 0. Lowering it is destructive and confirms first: `dropPersonData()` deletes that person's income/variable expenses/budget/goals/debts, and `redistributeShares()` spreads their slice of each shared expense across whoever is left so no money is left orphaned.
- `refreshPeopleUI()` rebuilds every person-dependent control in one place (all the `.seg` pickers, the split options, the names inputs in Ajustes) and publishes `--cols` / `--cols-sm` for the per-person grids. Call it after any roster or name change instead of touching those controls directly. With a single person it also hides the "who?" pickers and the split field entirely.
- Colors come from `PERSON_COLORS` by position (`personColor`, `personTagClass`), so charts and tags stay consistent as people are added.
- Who-owes-whom is `netBalances()` → `settlements()`: with two people it's the same single line as before, with three or four it greedily nets the debts into the fewest transfers.
- `f.locked` on a fixed template is a delete guard, not a freeze: it disables ✕ on the template row in Ajustes **and** on every loaded expense card in Gastos whose `desc` matches it (`lockedTemplateFor()`), while ✎ and the amount stay editable. The same padlock lives on the gastos posibles rubros.
- **A fixed expense can be personal**, not just shared (one person's monotributo). The recurring template in Ajustes carries an `owner` (`fixed[].owner`: a person id, or absent = shared, cycled with `cycleFixedOwner()`), and picking that chip in the add-expense modal preselects the split via `splitForOwner()`. The Gastos fijos block then filters the list with `renderFixedTabs()` into `Compartidos` + one tab per person, derived from `expenseOwner(ex)` — which reads the expense's own `shares`, so it needs no extra field and classifies pre-existing expenses correctly. The tabs filter **only the list**: the Totales below stay the whole month, or the chain would stop adding up.

**State → render flow**: every mutation (add/delete/toggle expense, add/remove income, change names or FX rate) follows the same pattern: mutate the in-memory object → persist via the relevant `save*()` function (fire-and-forget async, wrapped in try/catch) → call `render()` (or `renderIncomeLists()` for income-specific UI) to redraw affected DOM sections from scratch. There is no diffing — sections are fully re-stringified and reassigned to `innerHTML`.

**The money chain** — the single source of truth for every "how much is left" figure in the app is `financeFor(person, monthKey)`. It walks one person's month in the order the Gastos tab lays it out:

```
ingreso − su parte de los gastos fijos − sus gastos variables − lo que tiene presupuestado gastar − excedente de gastos diarios = ahorro
```

Gastos diarios consume the Salidas + Gustos pool, which is already subtracted in full as part of the budget: only the amount *over* the pool (`excedente`) lowers ahorro, and an unspent remainder does **not** raise it (it stays reserved until the month ends).

and returns every intermediate saldo (`afterFijos`, `afterVar`) plus `propio`/`compartido`/`podes` — what this person has budgeted per rubro (`budgetTemplates[person]`) plus their equal share of the shared rubros (`budgetTemplates.shared`). The amounts are no longer auto-suggested percentages of what's left: they're whatever was set in Ajustes, and the Gastos block only reads them. The Gastos tab is a stack of `.card` blocks in chain order — Saldos iniciales, Gastos fijos, Gastos variables, Gastos posibles (just Compra dólares, closing Saldos = afterVar − dólares; the 50/30/20 comparison and the Salidas/Gustos split live in Ahorro › Cómo venís este mes), Gastos diarios — each with sub-tabs filtering *only* its list (fijos/variables add `Compartidos`; the rest are one tab per person), and each closes with a "Saldos" step (`.sld-*`, `renderBlockSaldos()`) with the running saldo at that point. In Ingresos (`incomeTabs`, `currentIncomeTab`: the person columns shown, "+ Agregar ingreso" preselects that person, the según-ingresos preview only in Todos), Saldos iniciales (its own `startTabs`, `renderStartSaldos()`) and fijos/variables the Saldos follow the sub-tab (`renderTabSaldos()`): `Todos` (Ingresos, Saldos iniciales) / `Compartidos` (fijos/variables, where that tab also filters the list to shared expenses) shows one card per person, a person's tab shows only theirs (titled "Saldo") — always that person's full-month number, not the filtered list's. Compra dólares' amount is always the person's call; editing it also re-saves the stored Salidas/Gustos rubros 60/40 (`redistribuirWantsSegunDolares()`) so Ajustes matches, though the chain computes them itself. The Ahorro tab's headline number, its month-by-month history, and its 50/30/20 bars all read from the same function, so they can't drift from Gastos. If you change how any step is computed, change it in `financeFor()`, not in a renderer.

**Everything is split `Compartido` / one tab per person.** Gastos fijos and variables have a template list in Ajustes plus a modal whose `¿De quién es?` picker offers `Compartido` + each person, and the Gastos tab lists the entries actually loaded for the month. A shared entry stores `paidBy: 'shared'` plus a frozen `shares` map (equal parts at load time) and generates **no debt** — `netBalances()` skips it, because each person put in exactly their part. `entryShareOf()` turns one entry into one person's slice, and `redistributeShares()` re-splits shared entries when someone leaves the space. Gastos posibles follows the same `Compartido`/persona split but has no per-month entries: its rubros live only in Ajustes and the Gastos block renders them read-only.

**Key derived calculations** (in `render()`'s call graph):
- `renderCharts()` → `renderBalance()` — computes net debt between A and B across *all* expenses (not just current month) by summing each person's owed share vs. what they actually paid.
- `incomePctA()` — proportional income split (used when an expense's `splitType === 'income'`), converts any USD income entries to ARS using the manually-entered `fx` rate before comparing.
- Recurring expenses: marking a recurring expense paid (`togglePaid`) auto-generates the next month's copy via `addMonths()`, and bumps `cycleCount`; if `adjustPct > 0` and the new cycle is a multiple of 3, the amount is escalated by that percentage.

**Mobile navigation**: at `max-width:479px` the top `#tabs` and the floating `.fab` are hidden and replaced by `#bottomNav` (`.bnav`), a floating glass bar — Ingresos · Gastos · + · Deudas · Ahorro — modeled on the bottom nav of the project in `inspo/app` (git-ignored reference material). Its tab buttons go through the same `switchTab()`, which keeps both navs' `.active` in sync; the center + calls `openDailyModal()` like the `.fab`. It is hidden with the `.fab` while there's no couple code and while a modal is open. At the same width the header's icon row (`.head-right`) collapses behind a single `#headMenuBtn` and becomes its dropdown panel (`.app-head.menu-open`, `toggleHeadMenu()`): each icon shows its `aria-label` as text via `::after`, and the icons that own a popover (dólar, sesión — the ones with `aria-haspopup`) open it inline inside the panel instead of closing it. Header order (desktop and ≤479px; 480–600px keeps the icons row under the title): title + icons/menu, then the month selector full width, then the pages. Today's date is an icon in the icons row (`#dateBtn`, a calendar with the day number drawn by `renderTodayDate()`), whose popover/menu label reads "Miércoles 21". Any new header icon only needs a meaningful `aria-label` to show up correctly there.

**Global view (Vista)**: the header's `#viewBtn` (people icon, hidden with a single person) opens a popover — "Compartido / Todos" + one option per person — that moves every block's sub-tab at once via `applyGlobalView()` → `syncTabsToGlobalView()`. Tabs that accept a shared view (`currentIncomeTab`, `currentStartTab`, `currentFixedTab`, `currentVarTab`, `currentResumenTab`) always follow it; person-only ones (`currentBudgetTab`, `currentDailyTab`, `currentDeudasPerson`, `currentAhorroPerson`) follow only when a person is picked. Each block's own tabs still work independently afterwards. The choice is a per-device UI preference in localStorage (`global_view`) and is applied at startup. A new block with sub-tabs should be added to `syncTabsToGlobalView()`.

**Collapsible blocks**: every `.card` with a `.section-title` in Ingresos, Gastos, Deudas and Ahorro gets a circled chevron button top-right from `setupCollapsibleCards()` (runs once at load; `data-collapse="off"` opts a card out — the totals-only cards and "Entre ustedes"). Collapsing is pure CSS (`.card.collapsed`): it hides list rows (`.bill` except `.bill-total` and their `.bill-occurrences`, while a Totales row stays expandable with everything under it, `.income-entries`, `.goal`, `.sv-row`, `.empty`, `.collapse-body`) and keeps title, button, tabs, totals and saldos, so renderers need no changes — just use those classes. Which cards are closed is a per-device UI preference in localStorage (`collapsed_cards`), not couple data.

**Simplificada / detallada**: the header's `#detailBtn` (`toggleDetailMode()`, per-device `detail_mode` in localStorage) closes every collapsible card at once (simplificada) or opens every card *and* every expandable row (detallada). Rows work through `detailMode` + `isOpen(set, key)`: in detailed mode each `expanded*` set stores the rows closed by hand instead of the ones opened, so everything starts open without knowing each renderer's keys. **Always read an `expanded*` set through `isOpen()`**, never `.has()` directly, and add any new `expanded*` set to the list that `toggleDetailMode()` clears.

**Confirmations**: every delete (and other actions worth confirming) goes through the one `openConfirmModal(message, onConfirm, opts)`. For the two whole-month actions — "Borrar mes" (`clearMonth()`) and "Copiar al mes siguiente" (`copyMonthToNext()`) — `opts.confirmWord` adds a safety step: the OK button stays disabled until the person types that month's name (the month being cleared, or the destination month for a copy), compared ignoring case, accents and extra spaces. Use `confirmWord` for any new bulk action; single-item deletes don't need it.

**Charts**: category and payer breakdowns are rendered as hand-rolled SVG pie charts (`pieSvgHtml`/`arcPath`/`polarToCartesian`) — no charting library.

**i18n**: all user-facing strings are hardcoded Spanish (Argentine locale — `es-AR` for `Intl.NumberFormat`/date formatting, ARS as the default currency). There's no translation layer; don't add one unless asked.

## Conventions to preserve when editing

- Keep everything in the one HTML file unless the user asks to split it up — GitHub Pages serves it as a static file with no build step.
- Use the `store.get`/`store.set` abstraction (backed by Supabase) for anything that needs to persist — don't reach for `localStorage` as a source of truth; it's only used to remember which couple code this device last used (`couple_code` key) and per-device UI preferences like `collapsed_cards`, not for actual data.
- Key everything by person **id**, never by name and never by a hardcoded `'A'`/`'B'` — iterate `pids()` and resolve labels with `nameOf(id)`. Any new per-person UI belongs in `refreshPeopleUI()`, and any new per-person data structure needs a slot created in `setPeople()` and cleanup in `dropPersonData()`.
- `escapeHtml()` is used when interpolating user-entered text (`desc`, income `label`) into `innerHTML` — keep doing this for any new user-text interpolation to avoid XSS via the shared/multi-editor storage.
- Every `couples` row is shared by everyone who knows that couple's code — there is still no per-person auth within a couple, only isolation *between* couples.
